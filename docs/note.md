## CSR : Coordinate Reference System

座標参照系

「座標の数字が実際に地球上のどの位置を表すのか」を定義するルール

座標値（ex 139.6917, 38.3255）
＋　基準となる地球モデル
＋　座標の表現方法
＋　必要なら地図投影法

これらが定義されて初めて地球上の位置として解釈できる

### 地球　→　地図への変換

球体の地球を平面の地図にCSRを用いて変換が必要

※ 球面を完全に歪みなく平面にすることはできない

### CRSの種類

1. Geographic CRS : 地理座標系
   代表例　EPSG:4326 / WGS 84
   位置を緯度と経度で表す
   Longtitude: 139.xxx
   Latitude: 35.xxx
   → 距離を測るのは向かない

2. Projected CRS : 投影座標系
   地球上の位置を平面に投影
   X = xxx m
   Y = xxx m
   というm単位の座標で表す
   → 距離や面積の計算ができる

### EPSGとは？

CRSを識別する番号

- EPSG:4326　→　WGS84という地理座標系

- EPSG:6677 → JGD2011/Japan Plane Rectangular CS IX
  日本の平面直角座標系IX系
  東京周辺で距離・面積を扱う場合に使える投影座標系

### Reproject（再投影・座標変換）

地理座標系と投影座標系をそれぞれCRS情報だけ書き換えてはいけない
EPSG:4326で作成されたデータをEPSG:6677に変換はNG（データは変換されない）

中身のデータ変換まで完全に変換する場合は**Reproject**が必要

### プロジェクトCRSもある

異なる複数のCRSのデータが混在する場合がある
QGISではこれらをOn-the-flyで変換し、同じ地図上で重ねて表示できる
各レイヤーのCRS情報を確認する癖をつける

## Buffer処理

すでに作ってあるpointレイヤーを元に一定距離のPolygonレイヤーを新たに作成する

pointの半径〜mの円（polygon geometry）が表示される

この場合は距離を扱うためCRSは東京の場合EPSG:6677を使用。大事なのはEPSG:4326の地理座標系(Geographic CRS)は座標（degree）なので距離計算には適さない。

800m bufferとは中心からの直線距離800m圏内を表す

## Clip -> Spatial join -> Select by Location

### Clip

あるpolygonの範囲内だけを切り出す処理
（Geometryそのものを切る）

QGISではvector overlay -> clip

## Spatial Join

位置関係をキーにjoinする
（通常のデータ分析はidのような共通キーを使う）

### join attributes by location

predicate

- within : pointがpolygonの中にある
  　point within polygon

- contains : polygonがpointを内包している
  polygon contains point

- intersects : Geometry同士が少しでも接触している、重なってる

### select by location

位置条件に合うFeatureを選択（ハイライト）する処理

## 確認

1. Buffer
   point, line, polygonなどの入力geometryから、指定距離の領域をpolygonとして生成する処理
2. Clip
   Input layerは切られる側、overlay layerは切り抜き範囲を定義するpolygon
3. Spatial join
   通常は共通のidなどを使用してjoinするが、spatial joinはwithinやintersectsなど空間的位置関係を結合条件に使う
4. within / contains
   withinは含まれる側から見た関係、containsは含んでいる側から見た関係を表す
   point within polygon
   polygon contains point
5. intersects
   2つのGeometryが１点でも共通部分を持つ場合にTrueとなる判定条件。
6. Select by location / Clip
   Select by Locationは既存Featureを選択状態（ハイライト）にする。ClipはGeometryを実際に切って新しいレイヤーを作る

## 確認

- なぜ武蔵野市境界だけでなく、1.5km外側まで分析範囲を広げるのか?
  武蔵野市は市域が比較的小さく、市境付近の住民が市外の駅を利用する可能性があるため。行政境界だけで鉄道駅を抽出すると、実際には利用可能な周辺駅を除外してしまうため、1.5kmのバッファを設けて分析対象範囲を広げた。
- raw/とprocessed/を分ける理由は何か?
  raw/には取得した元データを変更せず保存し、processed/にはClip、再投影、Joinなどの加工後データを保存する。元データを保持することで、処理をやり直したり分析過程を再現しやすくなる。
- 行政区域データをEPSG:6677へ再投影する理由は何か?
  元データが別のCRSであるため、東京周辺で距離・面積をメートル単位で扱いやすいEPSG:6677に再投影する。今後のBufferや距離計算を一貫した座標系で行うためでもある。
- 人口CSV単体では地図上にPolygonとして表示できないのはなぜか?
  人口CSVには人口や世帯数などの属性値とメッシュコードはあるが、Polygon Geometryそのものを持っていないため。地図上で面として表示するには、同じメッシュコードを持つ500mメッシュ境界データとJoinする必要がある。
- 人口統計CSVと500mメッシュ境界を結合するには、何が必要か?
  両方のデータに共通するメッシュコードが必要で、境界データ側ではKEY_CODEをJoin Keyとして利用する。
- データ年度が異なる場合、分析上どのような注意が必要か?
  人口、鉄道、土地利用などのデータ年度が異なると、駅の新設・廃止、人口変化、土地利用変化などが反映される時点が異なるため、同一時点の都市構造を厳密に比較しているとは言えない。したがって結果の解釈時に年度差をLimitationsとして明示する必要がある。

## 確認

- なぜ人口CSVだけではコロプレスマップを作れないのか。
  人口CSVは人口値の統計表データであり、polygonなどgeometryを持たないため、そのままでは地図上の面として描画できない。境界メッシュデータと結合してコロプレスマップを作成する。
- JoinでKEY_CODEを使う理由は何か。
  人口CSVと境界メッシュデータの両データで同一の500mメッシュを一意に識別する共通キーのため
- Join Keyの型が異なると何が起こり得るか。
  joinする際に型が異なると認識されず正常にjoinできない可能性があるため
- Join結果をGeoPackageへExportする理由は何か。
  Join設定はプロジェクト上の一時的な関連付けのため、人口属性付きPolygonとして後続処理に安定して使用できるようGeoPackageへ保存する。
- ClipとJoinは、それぞれ何を変える処理か。
  ClipはポリゴンなどGeometryの対象範囲を切り取る処理。
  joinは別のデータの属性を対象Featureに追加する処理
- Natural BreaksとQuantileの違いは何か。
  Natural Brreaksはクラス内のデータのばらつきを小さくし、クラス間の差が大きくなるように境界を決める。そのため自然なデータの偏りを可視化できる。
  Quantileは各等級のデータ数が均等になるように割り振るため、上位〜％など均等な割合の統計値などを把握しやすい。
- 平均人口と中央値人口の両方を見る理由は何か。
  極端な大きさのデータがある場合平均値が外れ値側に移動するため正しい説明ができない。
  中央値はデータの幅によらず中央に位置する値を見るため極端な値の影響を受けづらい。
- 人口分布と駅位置が近く見えても、なぜ因果関係とは断定できないのか。
  人口分布には駅までの距離のほか、様々な居住環境（家、学校、病院、公共施設、交通手段など）の影響を受けるため、直接的に駅が近いから人口が多いとは断定できない。人口分布と駅位置に相関関係がある可能性は考えられる。また人口集積が鉄道整備を促したという逆因果の可能性も考えられる。

- 圏外メッシュは全体の54%（37個）

## 今後の展開

今回の分析により駅は遠いが人口の多い場所が確認された。これは駅周辺に人口が集中するという直感に反するものであり、駅アクセス性以外にも様々な居住に関係する要因が考えられ、次のような仮説を立てることができる。
武蔵野市北部中央の高人口・駅800m圏外地域では、どのような土地利用や交通条件が人口集積を支えているのか。

## 確認

- なぜ800mか。
  一般的な歩行速度（4~5km/h）で徒歩10分程度の直線距離として初期設定。
  絶対的基準ではなく、600mや1,000mでも感度分析する。
- なぜPolygonのintersects判定ではないか。
  端が少し重なるだけで圏内になる問題を避け、判定を明確にするため代表点距離を使った。
- なぜ市外駅も含めるか。
  行政界と生活圏は一致せず、市境住民が市外駅を利用する可能性があるため。
- 高人口をどう定義したか。
  恣意性を明示したうえで、対象内のP75以上という相対基準を採用した。
- 最大の限界は何か。
  直線距離、メッシュ内人口分布の不均一、境界メッシュ、バス未考慮、2020年データである点。
- 次にどう改善するか。
  道路ネットワーク到達圏、バス停・運行頻度、土地利用、年齢構成を追加し、複数閾値で結果の頑健性を検証する。
- メッシュPolygonが駅Bufferと少しでも交差すれば圏内、としなかったのはなぜか。
  メッシュPolygonと駅800m Bufferが少しでも交差すれば圏内とすると、メッシュのごく一部だけが800m圏に入った場合でも、メッシュ全体を圏内と判定してしまうためである。500mメッシュ内でも駅までの距離には幅があり、わずかな交差を基準にすると圏内メッシュを過大に判定する可能性がある。そこで今回は、完全メッシュの代表点から最寄駅代表点までの直線距離で統一的に分類した。ただし、この方法もメッシュ内部の距離差や道路上の徒歩距離は反映しない。
- Clip前の完全メッシュから代表点を作る理由は何か。
  市境でClipすると、市境にかかるメッシュの形状が一部分だけになり、その形状から作成した代表点は元の500mメッシュ中心からずれてしまうためである。人口値は元の完全な500mメッシュ全体に対応しているため、アクセス距離も元メッシュの代表点を使って計算することで、人口値と距離の空間単位を揃えた。
- 800m BufferをDissolveする目的は何か。
  複数駅の800m Bufferが重なる部分の内部境界をなくし、駅アクセス圏全体を1つの連続したPolygonとして扱うためである。これにより、どの駅のBufferかではなく「いずれかの駅から800m以内か」を判定しやすくなる。また、Spatial Joinなどを行う場合に、複数のBufferと重なることで同じメッシュが重複して結合されることを防ぎやすい。
- P75を使う利点と、注意点は何か。
  P75を使うことで、対象メッシュのうち人口が上位25%に当たる地域を、データ分布に基づいて抽出できる。単純に「人口4,000人以上」などの固定値を任意に設定するよりも、武蔵野市内で相対的に人口が多い地域を明確に定義しやすい。

  一方、P75は対象範囲・年度・メッシュ数によって値が変わる相対的な基準であり、行政上の高人口地域や交通政策上の優先地域を示す正式な基準ではない。また、閾値付近のメッシュを機械的に分けるため、P75をわずかに下回るメッシュが重要でないとは限らない。

  今回の場合：武蔵野市対象メッシュのP75は4,420人であり、人口4,420人以上を「相対的な高人口メッシュ」と定義した。

- 圏外人口のSumを武蔵野市の圏外人口と断定できないのはなぜか。
  市境にかかる500mメッシュの人口値には、武蔵野市外に居住する人口も含まれており、市境でClipしても人口値は面積按分されないためである。また、代表点が800m圏外であるメッシュについて、メッシュ人口全体を圏外人口として集計しているが、実際には同じメッシュ内に800m圏内の場所が含まれる可能性もある。そのため、Sumは「圏外に分類されたメッシュの人口値合計」であり、厳密な武蔵野市の駅800m圏外人口ではない。
- この分析だけで「公共交通空白地域」と言えない理由を3つ挙げる。
  - 今回対象としているのは鉄道駅だけであり、バス停、バス路線、運行本数などを考慮していないためである。
  - 駅までの距離はメッシュ代表点から駅代表点までの直線距離であり、道路ネットワーク、踏切、河川、駅出入口など、実際の徒歩経路を反映していないためである。
  - 500mメッシュ全体を代表点によって圏内・圏外に分類しており、メッシュ内　部の住民分布や場所ごとのアクセス差を表現できないためである。

  追加できる論点としては、次のものがある。
  - バスの運行頻度や時間帯
  - コミュニティバス
  - 自転車による駅アクセス
  - 高齢者など利用者属性
  - 駅までの坂道や道路環境
  - 目的地までの所要時間

  したがって今回抽出した地域は「公共交通空白地域」ではなく
  **鉄道駅への直線距離によるアクセス課題候補地域**
  となる

## 確認

- なぜ100m土地利用を500mへ集計したか？
  人口が500m単位で公表されているため、分析単位を合わせる必要があるから。100mデータを使うことで、500m内部の土地利用構成を割合として保持できる。

- なぜ人口メッシュを市境でClipしてから集計しない？
  人口値が元500mメッシュ全体の値であるため。土地利用も元メッシュ全体で集計し、分子・分母の範囲を一致させた。市境メッシュは参考候補として分離している。

- 建物用地割合が高ければ因果関係が証明できるか？
  できない。土地利用と人口の空間的な対応を示す記述分析であり、他に住宅供給、地価、バス、施設、歴史的経緯など交絡要因がある。

- 業務で次に改善するとしたら？
  道路ネットワークによる徒歩時間、駅出入口、バス運行頻度、用途地域や建物用途を追加し、複数のアクセス手段と居住環境を統合する。

## 考察

2019年10月の平日昼間の推計滞在人口は、武蔵野市南部の鉄道沿線、とくに駅周辺を含む1kmメッシュで高い階級を示した。一方、Day 5で抽出した市北部中央の高居住人口・駅800m圏外の500m候補を含む1kmメッシュは、最高階級には該当しなかった。このことから、居住人口が多い場所と平日昼間の滞在人口が多い場所の分布は、必ずしも一致しない可能性がある。ただし、居住人口は2020年国勢調査の500mメッシュ、滞在人口は2019年の1kmメッシュの推計値である。対象年・集計単位・算出方法が異なるため、数値の直接差分や因果関係の判断は行わない。

## 確認

- 「月内の平均的な1日」と「1か月の延べ人数」はどう違うか。
  平均的な1日は、2019年10月の対象となる平日の昼間の1日あたりの平均。延べ人数は対象日ごとの人数を合計したもの。
- なぜ1kmの値を500m候補へそのままコピーしないか。
  推計範囲がそもそも異なるため。1kmの値を各500mに複製すると、同じ人数を繰り返し数えることになり、500mごとの値を測定したかのように見えてしまいます。
- Clip後の1kmメッシュのSumを武蔵野市の滞在人口と言えるか。
  市境を跨ぐメッシュも存在し、それらは武蔵野市外まで含めたメッシュ全体の推計値であるため武蔵野市の滞在人口とは言えない（市内分を過大に計上し得る）。
- 駅周辺で高くても鉄道乗降者数と断定できない理由は何か。
  現時点で鉄道利用を判定できるデータはなく、鉄道の他バス、タクシーもしくは別目的で駅周辺を利用する人たちも当然いるため。
- 2019年の人流と2020年の人口を並べるとき何を注記するか。
  人流は1kmメッシュの平日昼間、GPSに基づく推計、国勢調査人口は500mメッシュの居住人口であり、データの作成年、単位、方法などに違いがあるため直接的な比較は難しい。年度差の観点では交通インフラの変化により人流が変化する可能性や、居住人口の変化なども考えられるが、実際にそういった事象を確認した場合に考慮する。
